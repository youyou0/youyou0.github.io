01The case

Problem

Everyone instructs the agent in their own corner.

No shared model of the work, no contract between its steps, no boundary on which rules apply where. Instructions pile up, overlap, and sometimes contradict each other.

Goal

Model the work first, then put the agent inside it.

The steps, what each one receives and hands over, where the agent runs and within which limits, and where a person decides.

My part

The frame, the cockpit, the rules.

I designed them, I built the cockpit, and I work in them every day.

02The idea

Code and agents, side by sideWe already know how to do this

An agent is the same thing. Only the language changes: C# becomes sentences.

In codeWith an AI agent
Contractthe signature: int Add(int a, int b)what the work receives, what it hands back, and when it is done
Bodythe C# codethe request, in plain language
Proofthe unit testthe same proof, run before and after the change
Harnessthe runtime around the code: its settings, what it may access, the checks that stop iteverything around the model during one run: what it sees, its tools, its limits
Loopa while loop, until the exit condition is truecall a tool, read the result, again, until the end condition: the tests pass
Graphthe architecture: which function calls which, in a fixed orderthe chain of steps, fixed in advance; one step can hold a loop

A function

A few lines. Same input, same output. It can only do what its code does, and the compiler and its tests check it.

An agent’s task

Hours of work across many files. It can vary from one run to the next, and do anything it is allowed to: files, git, servers. Only what we set up checks it.

Bigger, less predictable units: modelling and architecture matter more, not less. Nobody ships ten thousand lines without functions, interfaces and tests.

Each level came to fix a limit of the one before. Prompt, context and skills decide what the model knows. Loop and graph decide how its calls are chained: in a loop the model picks the next step; in a graph, we fixed it in advance.

03How an agent works

The harnessEverything around the model during one run

The model is a powerful horse; the harness is the gear that controls it: what it sees, what it may do, when it stops.

It does not make the model smarter. It makes its work predictable, checkable, and stopped wherever a decision is mine.

What it sees
CLAUDE.md, the rules of the repository, always loaded; my request; the notes the work needs.
Know-how
skills: written procedures loaded at the right step. Open a thread, write a session note, write the week’s recap.
Limits
hooks: small scripts that check an action before it runs and can stop it, such as staging every file at once. Permissions: what waits for my yes, such as a push.
Specialists
sub-agents with fewer tools: one maps what a change could break and can only read; one writes the tests before the change and never touches the code it tests.

Its memory: my notesWhere what lasts between runs is kept

A run forgets everything when it ends. The notes are what the next run reads back.

Three kinds of memory, as in the agent literature: what happened (the session notes and threads), what we know (topic notes, decisions), and how to work (the conventions, and in the repository, CLAUDE.md and the skills). Each fact has one home, so nothing lives only in a chat.

  • Threads one piece of work each, until its verdict
  • Session notes what happened, day by day
  • Topic notes what we know about one part of the code
  • Decisions a choice and its why
  • How we work the steps, the conventions
  • Entry points home, open threads, one hub per module

Kept up to date at the end of each session: the day’s story goes into the session note, and what lasts is moved up into the topic note.

The loopThe tools it calls, and where it stops

Inside one run, the agent goes round: the model picks a step, a tool does it, the result comes back, until an end condition is met.

Who builds a loop chooses two things: which tools it gets, and when it is good enough to stop.

My loopsThe tools it getsWhere it stops
My own sessionsthe agent’s built-in tools, and my own: a page that draws each test before and after the changeI review the result
The test writerread the code, write and run tests; nothing elsethe tests exist, and fail on the code as it is
The impact readerread and search onlya map of what the change could break, or a written “nothing at risk”

The graphWe fix the shape of the calls

A loop and a graph coexist. Explore with a loop; once a procedure stops changing, fix it as a graph.

In a graph the steps, their order and the ways back are written in advance. A step can be a tool, a call to the model, a whole loop, or a person.

04In practice

One piece of work, A to FMy graph, followed through one thread

A thread is one note in my vault that carries one piece of work from what was seen to the verdict. Every session starts by reading it and ends by writing into it, so the work outlives any chat; the cockpit reads its header to show what step it is at and who it waits for. Each step writes its own part; the order of the steps is held by written instructions today, not by code. Here is a demo thread filling in.

Two directions on top of each other

Now

Need

On a 24-hour highway recording, the lanes learned for the two directions came out on top of each other instead of side by side.

Done when: no learned lane overlaps the other direction’s, on the test cases and the replay. Not in scope: why a lane spills over in the first place.

Findings
  • Nothing compared the two finished lanes or cut one against the other. observed, in the code
  • A lane can swing sideways over its neighbour mid-image while staying the busier one there. observed, on a test case
  • Ruled out: the busier direction keeps the shared zone. Killed by the swinging case.
Decisions
  • The busier direction keeps the shared zone. first rule, later replaced
  • My call: real lanes are parallel, so the lane whose shape is not coherent gives way; traffic comes second.
  • The measures and thresholds the agent proposed: accepted.
Plan

Split the overlap into separate shared zones; in each, cut the lane that breaks from its own neighbours. One place in the code changes; nothing else reads it. searched by the impact sub-agent

Verdict

One rule holds the whole graph together: when the result only passes with a patch, go back to Understand, not to Build. Patching means the base is wrong.

Getting better: LLM OpsHow we know a change to the rules made it better

Without this part, nobody knows whether a change to a rule made the agent better or worse.

The method Andrew Ng teaches in his course on agentic AI: measure each run, count which step causes the failures, fix that one first, and replay before releasing.

Where I am, plainly. I have run it once, by hand, on the contract I wrote for pull requests: ten criteria drawn from a year of the team’s review comments, replayed on 15 past cases. It caught part of what reviewers had raised; where it missed, the checker had not been given the information. Most of the noise came from two badly written rules, and those are the next fix. None of it runs on its own yet.

05The result

What it changes

  • A → FEvery piece of work goes the same way, from what was seen to a verdict.
  • Before · afterEach change judged by a proof written before it, and replayed after it.
  • ReviewsReview comments answered in the code, each fix with a test that fails without it.
  • Written downDead leads with what killed them, and every cause with how sure it is.

Limits. Agents can be confidently wrong, so every cause is written with how sure it is, and a dead lead is reopened only on new data. Human review still finds what automated passes miss. And the rules take time to write at the start.

Key decision

The verdict is always mine

Context
An agent reads, tests and writes fast, and can be sure of itself while wrong.
Decision
The agent does the reading, the measures and the code; I set the domain rules and give every verdict, which can be no.
Set aside
Letting the agent close its own work.
Cost
Every piece of work waits for me at least once.
